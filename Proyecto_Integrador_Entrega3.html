1. Explicación e Implementación de Integración Continua (Travis CI / GitHub Actions)

💡 ¿Qué es un Servidor de Integración Continua (CI/CD)?

La Integración Continua (Continuous Integration - CI) es una práctica de ingeniería de software mediante la cual cada cambio realizado en el código fuente (un `git push` o un Pull Request) activa un servidor automatizado en la nube (como Travis CI o GitHub Actions) que descarga el proyecto, instala sus dependencias y ejecuta pruebas unitarias automatizadas.

Si alguna prueba falla, el servidor de CI marca la compilación como FALLIDA (FAILED) y bloquea la integración de dicho código hacia producción, garantizando que el sistema en vivo nunca sufra caídas.

1.1 Configuración de Travis CI (`.travis.yml`) y GitHub Actions

Para cumplir con los requerimientos técnicos y la rúbrica del curso, se configuraron dos motores de integración continua conectados directamente al repositorio de GitHub https://github.com/kdej94-coder/seguros-compare.git:

Archivo de Configuración de Travis CI (`.travis.yml`):

# Travis CI Configuration for SegurosCompare

node_js:

script:
  - npm test

1.2 Suite de Pruebas Unitarias Automatizadas (`test/app.test.js`)

Se construyó una suite de pruebas automatizadas ejecutada con el comando `npm test`. Al realizar un push, el servidor de CI ejecuta estas 3 pruebas clave:

  1. Prueba de Extracción Heurística Regex: Valida que los patrones de texto detecten correctamente coberturas amparadas en el PDF.
  2. Prueba del Motor de Scoring ("Mejor Opción"): Garantiza que la aseguradora con menor prima y mayor cobertura sea seleccionada correctamente.
  3. Prueba del Módulo de Autenticación: Valida el inicio de sesión del usuario y el rechazo de credenciales incorrectas.

2. Estrategia de Administración de Código (Git Flow Branches)

El código fuente se administra con dos ramas principales de ciclo de vida permanente y ramas temporales por requerimiento:

  • main (anteriormente master): Contiene únicamente el código estable publicado en producción para los usuarios finales (Milestone GA).
  • develop: Rama de integración continua donde se consolidan las funcionalidades probadas durante la fase de desarrollo (Milestone Beta).
  • feature/*: Ramas individuales creadas para desarrollar una tarea específica (ej. feature/pdf-engine, feature/login-modal), las cuales se integran a develop mediante Pull Requests (PR) previa aprobación de pruebas CI.
Flujo de Ramas y Despliegue (Git Flow + CI/CD)
[Feature Branch]
➔ (PR + Tests CI) ➔
[develop Branch (Beta)]
➔ (Merge Release) ➔
[main Branch (GA)]
➔ (Deploy Cloud) ➔
[Render App Live]

3.2 Delimitación del Alcance: Lo que NO se cubrirá en la Versión v1.0 (Out of Scope)

Con el objetivo de delimitar el alcance del producto y garantizar la entrega oportuna en la versión v1.0, las siguientes funcionalidades han sido catalogadas bajo la etiqueta out-of-scope / v2-future y se han diferido para futuras versiones del software:

Funcionalidad Fuera de Alcance (v1.0) Etiqueta Justificación Técnica de Exclusión
Base de Datos Persistente (PostgreSQL / MongoDB) v2-future La v1.0 funciona en memoria y archivos temporales para maximizar velocidad y privacidad de cotizaciones sin costo de infraestructura de BD.
Reconocimiento Óptico de Caracteres (OCR Tesseract) v2-future Los PDF de cotizaciones de las aseguradoras actuales son digitales vectoriales. El OCR para PDFs escaneados como imagen requiere alto consumo de CPU.
Envío Automático de Correos (SMTP SendGrid) v2-future Se priorizó la exportación directa a PDF/Impresión ejecutiva en la v1.0. El envío por correo se pospone a la v2.0.
Módulo de Pago de Pólizas en Línea (Stripe) v2-future El sistema es un comparador de toma de decisión técnica, no una pasarela de venta directa de pólizas.

4.1 Componentes de Infraestructura

  1. Repositorio Central: GitHub (`main` y `develop`), que almacena el código fuente, la documentación y los scripts de prueba.
  2. Servidor de CI/CD: Travis CI y GitHub Actions Runners, encargados de verificar la integridad del código en cada push.
  3. Servidor de Aplicación: Node.js con Express, encargado de servir la interfaz estática (`/public`) y exponer la API REST.
  4. Servidor de Producción Cloud: Render.com Web Service, que ejecuta la aplicación de forma pública con SSL (HTTPS).
